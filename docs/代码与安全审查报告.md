## 二、安全类问题（按优先级）

### S1 · SSRF：扫描接口可被用来访问内网与云元数据【高危 · 已修复】

- **位置**：`server.py` `POST /api/scan`（原文 50-85 行）
- **现象**：接口直接拿用户输入的 URL 调 `requests.get`，任何校验都没有。攻击者可以提交：
  - `http://127.0.0.1:8000/`、`http://10.0.0.5/`、`http://192.168.1.1/` —— 探测内网
  - `http://169.254.169.254/latest/meta-data/` —— 云厂商元数据（AWS/GCP/Azure 通用），可能拿到临时凭证
  - `http://localhost:6379/` 之类的非 HTTP 服务
- **影响**：公开部署的 Render 实例等于给公网开了一个内网代理；云元数据一旦读出，可能升级为账号接管。这是 OWASP 里最典型的 SSRF。
- **加剧因素**：
  - `requests.get` 默认**跟随跳转**，即使加了 URL 黑名单，一个 `302 → http://127.0.0.1` 就能绕过；
  - 没有限制协议，`file://` 等也会进到 requests 里。
- **修复**（新增 `guard.py`，`server.py` 接入）：
  1. `normalize_target()`：只允许 http/https、禁止携带账号密码、限制端口为常见 Web 端口白名单、补全 scheme、去掉 fragment。
  2. `assert_public_target()`：请求前解析域名，任何解析结果落在回环/私网/链路本地/保留网段（含 `169.254.0.0/16`、`fd00::/8`）一律拒绝。
  3. 所有出站请求 `allow_redirects=False`，从根上掐断"跳转到内网"的绕过路径。
  4. 校验失败返回 `400` 并给出明确原因，而不是 500。

### S2 · 无鉴权、无限流：接口可被当作免费扫描器 / 免费 LLM 代理【高危 · 已修复】

- **位置**：`server.py` `POST /api/chat`、`POST /api/scan`
- **现象**：任何人都能不登录调用。`/api/chat` 每次调用消耗你的 DeepSeek 额度；`/api/scan` 会从你的服务器 IP 向第三方发起几十个请求。
- **影响**：额度被刷爆（直接经济损失）、服务器成为别人扫描第三方的跳板（法律与封号风险）、免费实例被拖垮。
- **修复**：新增 `ratelimit.py`（进程内滑动窗口），扫描 6 次/分钟、问答 20 次/分钟，超限返回 `429` + `Retry-After`。生产环境应换成 Redis 计数或网关级限流。

### S3 · 扫描器主动向 `https://evil.com` 发请求【中危 · 已保留但说明】

- **位置**：`scanner.py` `check_redirect_trap`（原文 186-199 行）
- **现象**：开放式重定向检测硬编码外部域名作为"恶意目标"。
- **判断**：技术上必须有一个外部地址才能验证跳转，本身可接受；但要注意两点：① 扫描第三方站点时会从你的 IP 向该域名发请求，等于替目标做了跳转测试；② 不要用真实可注册域名（已被他人注册的情况不可控）。
- **处理**：改用保留示例域 `evil.example`，并在 README 的"已知限制"里写明"仅扫描你有权测试的站点"。

### S4 · 依赖不锁版本，构建不可复现【中危 · 已修复】

- **位置**：`requirements.txt`（原文 1-5 行，全部裸包名）
- **风险**：`openai` 从 0.x → 1.x 的破坏性升级会让 `OpenAI()` 直接不可用；Render 每次构建拿到的版本可能不同，出现"昨天能跑今天挂"。
- **修复**：改为带上下界的约束（`fastapi>=0.115,<1.0` 等），新增 `requirements-dev.txt`。

### S5 · 启动期创建客户端，缺 key 时错误滞后【中危 · 已修复】

- **位置**：`server.py` 19-22 行 `client = OpenAI(api_key=os.environ.get(...))`
- **现象**：没配 key 时应用照常启动，直到用户提问才 500；`os.environ.get` 返回 `None` 时 OpenAI SDK 会抛 `OpenAIError`，提示信息不友好。
- **修复**：改为 `get_client()` 延迟创建，缺 key 直接返回 `503` 并说明原因；同时延迟导入 `openai`，让扫描功能不依赖 AI 依赖是否装好。新增 `GET /api/health` 暴露 `deepseek_configured`，方便部署自检。

### S6 · 前端已有转义，但 class 拼接仍是注入面【低危 · 已修复】

- **位置**：`static/index.html` 148 行 `'<span class="badge ' + esc(f.severity) + '">'`
- **现象**：`esc()` 挡得住标签闭合，但把外部字段直接拼进 `class` 属性本身是不好的模式（一旦有人放宽转义规则就会变成属性注入）。
- **修复**：新增 `severityClass()` 白名单映射，只输出 `high/medium/low`。

### S7 · 问答接口无长度限制【低危 · 已修复】

- **位置**：`server.py` `ChatRequest`
- **风险**：超长 prompt 直接放大 token 消耗（配合无限流更糟）。
- **修复**：`message` 限制 1-2000 字符，`level` 限制 16，同时给 `max_tokens=1024`。

## 四、工程与前端问题

### E1 · 没有一个测试【已修复】

原来完全靠手工点页面验证，改一处怕崩一处。现在 `tests/` 下 62 个用例，全部使用假响应、零真实网络请求，覆盖目标校验、10 个模块的判定与误报回归、接口错误隔离/超时/限流。新增 GitHub Actions 在每次 push 时跑 `pytest`。

### E2 · 前端没有 try/catch，异常会卡在 loading【已修复】

这正是上次"扫描卡死"的同类问题：上次修的是变量名，但 `await resp.json()` 在服务端 500 或返回 HTML 错误页时同样会抛异常，页面永远停在转圈。现在 `runScan`/`sendMSG` 都有 `try/catch/finally`，失败显示原因，按钮在 `finally` 里恢复。

### E3 · 扫描期间可重复点击，无防抖【已修复】

增加按钮 `disabled` + "扫描中"文案，请求结束恢复。

### E4 · 报告下载可能被取消【已修复】

`URL.revokeObjectURL(a.href)` 紧跟 `click()` 执行，部分浏览器会在下载开始前就把 URL 释放。改为 `setTimeout(..., 0)` 里再释放。

### E5 · 后端返回结构重复且脆弱【已修复】

原来响应里 10 个字段名各写一遍（`check_xss`、`check_open_ports`…），前端也要按字段名逐个展开，加一个模块要改两处。现在统一为 `modules: {key: {...}}` + `empty_text` 映射，前端一个循环渲染完。

### E6 · 根路径 404【已修复】

README 要求用户手工访问 `/static/index.html`，直接打开域名是 404。现在 `GET /` 307 跳转到页面。

### E7 · 缺少 `.env.example`、`.gitignore` 不完整【已修复】

新增 `.env.example`；`.gitignore` 补 `.venv/`、`.pytest_cache/`、`.deps/`。

### E8 · 部署配置缺健康检查【已修复】

`render.yaml` 增加 `healthCheckPath: /api/health`，Render 可据此判断实例是否真的活着（冷启动后自动重试）。

## 五、仍建议改进（本次未做，按性价比排序）

1. **把 IP 固定到连接上**：当前是"请求前解析 + 校验"，理论上存在 DNS rebinding 窗口（校验时解析到公网 IP，实际连接时变成内网 IP）。彻底做法是自定义 `HTTPAdapter`，用已校验的 IP 建连并把 `Host` 头设回域名。
2. **线程超时后无法回收**：`asyncio.wait_for(asyncio.to_thread(...))` 超时后线程仍在跑（Python 无法强制杀线程）。免费实例 0.1 CPU 下，连续超时会短暂堆积线程。彻底做法是 `httpx.AsyncClient` 全异步，或把扫描放进独立进程池。
3. **限流状态在进程内存**：多实例部署时失效，应换 Redis 或网关注入。
4. **没有鉴权**：若继续公开，建议加"扫描前需登录"或邀请码，避免被滥用。
5. **XSS 判定上下文**：目前只判断"payload 原样出现"，可以在 HTML/JS/属性三种上下文分别构造 payload，减少误报。
6. **报告只有 JSON**：可以加 Markdown/PDF，或直接生成带排查建议的 HTML 报告。
7. **iOS/移动端样式**：当前卡片布局在窄屏下可用但未专门优化。

## 六、验证方式

```bash
# 单元测试（62 个，零真实网络）
python -m pytest -q

# 本地起服务 + 实测
uvicorn server:app --port 8123
curl -s localhost:8123/api/health
curl -s -X POST localhost:8123/api/scan -H 'Content-Type: application/json' -d '{"url":"example.com"}'
# 预期：10 个模块 status=ok，elapsed 约 6s

# SSRF 拦截验证（预期 400）
curl -s -X POST localhost:8123/api/scan -d '{"url":"http://169.254.169.254/latest/meta-data/"}' -H 'Content-Type: application/json'
```

实测结果（本机，2026-11-25）：

- `GET /` → `307` 跳转 `/static/index.html`
- `GET /api/health` → `{"status":"ok","version":"1.1.0","deepseek_configured":false,"modules":10}`
- 扫描 `example.com` → `200`，`summary: {ok: 10, timeout: 0, error: 0, findings: 8}`，耗时 6.0s
- 扫描 `http://127.0.0.1:8123`、`http://169.254.169.254/...` → `400` 拒绝
- 前端脚本用 Node 校验：语法通过，10 个卡片渲染正常，恶意 payload 全部被转义，超时模块显示"结果未知"
