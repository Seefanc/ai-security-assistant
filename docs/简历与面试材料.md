## 二、60 秒口头介绍（背下来）

> 这是我独立做的一个 Web 安全扫描工具。用户在网页上输入网址，后端并发跑 10 个检测模块——检查安全响应头、敏感文件、反射型 XSS、SQL 注入、CORS、开放重定向这些常见配置问题——结果以卡片展示，也能导出 JSON 报告，另外接了 DeepSeek 做安全问答。
>
> 项目里我自己最满意的有三点：一是把串行扫描改成 asyncio 并发，耗时从 51 秒降到 11 秒；二是踩了两个真实的坑——前端引用了未定义的变量导致页面一直转圈，还有扫描器自己把目标返回的数据塞进 innerHTML，等于被扫描的站点能反过来给我们注入脚本，后来统一做了输出转义；三是做安全审查时发现，我把它部署成公开服务后其实是个 SSRF 入口，任何人能让我服务器去访问内网和云元数据，于是补了目标校验、限流，也补了测试。

## 三、STAR 讲法（2 分钟版，按"问题—动作—结果"讲）

**背景**：想做一个能写进简历的安全方向项目，要求"真的能跑起来、有在线地址"，而不是本地 demo。

**任务**：一个人完成从后端检测逻辑、前端页面到部署上线的全部工作，并且要经得起"你自己是安全的吗"这类追问。

**动作**：

1. **功能层**：确定 10 个可自动化检测的点，每个模块只做"能给出明确证据"的检查（例如 SQL 注入只做报错型，先取基线再比对，避免把普通文案当报错）。
2. **性能层**：串行 51 秒不可接受，用 `asyncio.to_thread` 把阻塞的 requests 调用丢进线程池，`gather` 并发等待，每个模块 `wait_for` 10 秒超时。遇到的问题是"超时了但线程还在跑"，所以设计上只保证不影响整体响应，并在文档里写明这一限制。
3. **安全层（最关键）**：扫描器把不可信数据回显到页面 → 补 `esc()` 转义；部署成公网服务 → 补 SSRF 校验（私网/回环/链路本地/云元数据、非 http 协议、非 Web 端口一律拒绝），并关闭自动跳转；接口会被刷 → 加每 IP 限流。
4. **质量层**：补 62 个 pytest 用例（全部用假 Response，不依赖网络），加 GitHub Actions。

**结果**：线上可访问，10 个模块稳定返回；扫描 51s → 11s；审查出的高危项全部修复；改动前后有测试兜底，敢继续改。

## 四、高频追问与参考回答

### Q1：51 秒降到 11 秒，是怎么测的？数字可信吗？

**答**：同一台机器、同一个目标（httpbin.org，本身响应慢）、同样的 10 个模块，只改调度方式，改前改后各跑几次取稳定值。要主动说明：**这个倍率依赖目标响应速度**——如果目标本身很快，串行也没有 51 秒，倍率会小。真正的收益是"最慢的那个模块决定总耗时"，而不是固定快 4.6 倍。

**加分**：可以说"如果重做，我会用本地可控的测试服务（比如故意 sleep 1s 的 mock server）来测，基线更干净"。

### Q2：为什么用 `asyncio.to_thread`，不直接用 `httpx` 异步？

**答**：因为检测逻辑原本就基于 `requests`，同步改造成本低，`to_thread` 能一行把阻塞调用变成可等待对象。缺点是超时后线程无法被强制终止，极端情况下会堆积。更彻底的做法是全链路换 `httpx.AsyncClient`，但那样要重写所有探测函数的返回处理。**这是我在"改动量"和"彻底性"之间的取舍，我知道它不是最优解。**

### Q3：每个模块 10 秒超时，怎么定的？

**答**：单模块内部最坏情况累加（比如敏感文件 4 个路径 × 3 秒）不超过 10 秒，前端体验上 10 秒也还能接受；同时比 `requests` 单请求超时（3-5 秒）大，避免"模块超时"抢在"请求超时"前面触发。实测整轮 6 秒，10 秒有裕量。

### Q4：怎么避免误报？

**答**：三个手段。① **基线对比**：SQL 注入先请求正常参数，只有注入后才新增的报错特征才算命中；② **组合特征**：目录遍历不再用 `localhost` 这种到处都有的词，而是要求 `root:` 同时出现 `:/bin/` 这类结构；③ **内容校验**：`.git/HEAD` 必须是以 `ref:` 开头的 Git 内容，避免把 SPA 的兜底 200 页面当成泄露。这三条都写成了回归测试。

### Q5：还能误报吗？漏报呢？

**答**：能。反射型 XSS 只判断"payload 是否原样出现"，没有区分 HTML/JS/属性上下文，可能误报；端口扫描只做 TCP 连通性，不识别服务，CDN 后面的目标参考价值有限；WAF 拦截会让结果变成"未发现"（现在至少会标成 error 而不是安全）。README 里明确写了"不能替代专业渗透测试"。

### Q6：你说的 SSRF 是什么？为什么扫描器会有这个问题？

**答**：SSRF 是服务端请求伪造——攻击者让**你的服务器**去请求他想访问的地址。扫描器天然要"替用户访问任意 URL"，如果不做限制，就等于一个内网代理。典型的攻击是访问 `169.254.169.254`（云厂商元数据接口），可能读到实例的临时凭证。修复分三层：协议/端口白名单、解析后 IP 黑名单（私网、回环、链路本地）、关闭自动跳转（否则 302 能绕过前两层）。

**追问"你的修复够吗"**：诚实的回答是不完全够——DNS rebinding 仍然存在窗口（校验时解析到公网、连接时解析到内网），彻底方案是把已校验的 IP 固定到连接上，这我写在改进清单里没做。

### Q7：XSS 那个 bug 具体怎么发生的？

**答**：开放式重定向检测会读取目标返回的 `Location` 头，前端为了展示把它直接拼进 `innerHTML`。如果被扫描的站点返回 `Location: <img src=x onerror=alert(1)>`，这个脚本就在**我们的**结果页执行了。根因是把"扫描结果里的外部数据"当成了可信 HTML。修复是加统一的 `esc()`，所有外部数据（目标响应、用户输入）进 DOM 前都转义，class 名改成白名单。

**加分**：可以引申"输出编码要按上下文"——HTML 文本用实体转义，JS 字符串要额外处理 `</script>`，URL 属性要 `encodeURIComponent`，不能一套 `escape` 走天下。

### Q8：前端卡死那个 bug，怎么定位的？

**答**：页面一直转圈，但后端日志显示扫描正常返回。F12 打开 Console 看到 `Uncaught (in promise) ReferenceError: header_results is not defined`——改后端时把字段名改成了 `data.findings`，前端还在用旧变量名，异常发生在 Promise 里，没有冒泡到 UI，渲染函数中途崩掉，loading 永远不消失。教训有两条：**Promise 里必须 try/catch**，以及**前后端字段名要有一份约定**（这次之后我把响应结构统一成 `modules` 映射）。

### Q9：为什么没有数据库？

**答**：当前所有检测都是无状态的实时探测，没有历史记录和多用户概念。加数据库的收益是"扫描历史 + 报告分享"，成本是引入账号体系和数据清理问题。对个人项目来说我优先保证"打开就能用、不用注册"，所以没做。如果要有偿提供服务，第一步一定先加账号和配额。

### Q10：这个项目里 AI 具体做了什么？

**答**：`/api/chat` 接 DeepSeek，用 system prompt 约束"给具体可执行的加固建议，不要编造漏洞"。扫描本身**不依赖 AI**——检测是确定性规则，AI 只做问答和解释。这是刻意的：把不确定的模型放进检测结论里，会让结果不可复现。

**追问"为什么不做 AI 自动分析报告"**：可以做，但需要控制幻觉，比如把结构化检测结果塞进 prompt 并要求"只引用给定事实"，同时保留原始证据。这是下一步。

### Q11：如果并发再高，你的服务会怎样？

**答**：会先撞到线程池上限（`to_thread` 默认 `min(32, CPU+4)`），然后请求排队、超时率上升；限流是 6 次/分钟，正常不会到那一步。要扩展的话：异步化（httpx）→ 多实例 + Redis 限流 → 扫描任务队列 + 异步回调。

### Q12：代码里 `except: pass` 那么多，是不是坏味道？

**答**：是，而且我改了一部分。检测场景确实需要"单个探测失败不影响其它探测"，但不该**静默**——现在主请求失败会向上抛，服务层标成 `status=error` 并带原因；只有单个 payload 的失败才允许跳过。区分"容错"和"吞错"是这次审查的一个收获。

### Q13：如果面试官问"这项目是不是 AI 帮你写的"？

**答**：大方承认用了 AI 辅助（现在没人不用），但要能讲清楚**你自己做的判断**：为什么选报错型 SQLi 而不是时间盲注、为什么 10 秒超时、为什么 SSRF 要关跳转、误报怎么回归。**能讲清取舍的就是你的**。最好的证明是"我知道它哪里不行"——比如线程无法杀、DNS rebinding 没彻底解决、限流是进程内的。
